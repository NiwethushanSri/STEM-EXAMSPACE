# Phase 3A: Marking a script — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An admin or subject teacher enters an exam's questions and mark scheme; an admin approves markers and opens marking; markers press "Next script" and mark verified scripts on a computer or an iPad with Pencil, without ever seeing a name, saving as they work and submitting when every question has a mark; admins assign, take back and see what is left; a script ends at `marked`.

**Architecture:** Postgres (Supabase) holds the structure, approvals, units, holds, markings, marks and annotations, with every rule in `security definer` SQL functions; markers have no table access at all and read through those functions. A unit is a whole script or one question group of a script; a marking is one marker's pass on a unit and carries a kind, so Phase 3B adds second, seed and practice passes without changing tables. The marking screen is a client component that loads marking pictures through 120-second signed links (a storage policy lets a marker read only the current marking picture of a piece they hold), keeps an operation queue and saves through one SQL function with a revision number.

**Tech Stack:** Supabase (Postgres 17, pg_cron, Storage, Edge Functions on Deno), pgTAP; Next.js 16, React 19, pointer events, Vitest, Playwright; the Phase 2 processing server (Python 3.12 in Docker, pytest) for one clean-up step. No new npm or Python packages.

**Spec:** `docs/superpowers/specs/2026-11-20-web-platform-design.md`, sections 6.1 to 6.4 (approved 2026-11-20); also binding: 3 (anti-goals), 4.2, the last paragraph of 11, and 12 to 15. Master plan: `docs/owner/2026-11-functional-specification.pdf`, sections 17 to 20. Phase 2 hand-over: `docs/superpowers/2026-11-21-phase2-release-notes.md` ("Known limits", "Follow-ups for Phase 3", "Small fixes before launch"). Builds on branch `phase2-scripts` (not merged or deployed).

**Not in this plan (Phase 3B, a later plan):** double marking, seeded scripts, practice before live marking, lead marker review and settling, marker statistics, approval to `checked`, marker payments (spec 6.2 practice bullet, 6.5, 6.6). Also not here: a comments library, audio feedback, offline marking (Phase 5), drawing question areas on the page (the column exists; the drawing tool comes with AI suggestions), results (Phase 4).

## Where Phase 3B plugs in

- A second, seed, practice or re-mark pass is a new `markings` row with that `kind` and its own `marking_assignments` row. The unique indexes are per unit **and kind**; seed and practice passes may have many markers per unit (`unique (unit_id, kind, marker_id)`).
- `marking_units.state` describes the live pass only. 3B adds its own column for the check pass and moves scripts `marked` → `checked`.
- `marking_next` has one named place for "not the marker who did the first pass" and for mixing seeds in.
- `exam_marking` takes 3B's settings (sample, tolerances, switches for small subjects with their reason). `marker_approvals` stays per subject; 3B adds the per-exam clearance after practice.
- `markings.lead_note`, `markings.active_seconds`, `question_mark_history` and `marking_alerts` are written now and read by 3B's review, statistics and tolerance alerts. Payments count `markings` with kind `live`, status `submitted`.
- `question_marks.source` is `'marker'` today; the check constraint is widened for "suggestion accepted". `exam_questions.areas` and `mark_scheme_points` are what a suggestion needs.

## Global Constraints

- From the design, word for word: "Server time decides every deadline (UK time on screen, daylight saving handled)." "Private buckets only; pictures through signed links that expire within minutes, handed out after a permission check." "Markers receive marking pages only (name band removed) and see index numbers, never names." "Every staff action that changes a script, a mark, a structure, a boundary or a publication writes an audit row with a reason where the action asks for one." "Originals are never changed or deleted except by the retention rule." "No personal data in server logs."
- Anti-goals (a failure even if it works): "A marker sees a candidate's name, or can tell whose script it is from anything on screen except the index number." "A script is marked twice by mistake, or not at all without anyone noticing." "The original upload or scan is changed or lost; a mark changes without a record of who, when and why."
- Row-level security on every new table. Writes only through `security definer` SQL functions with `set search_path = ''`; `revoke execute ... from public, anon`, then explicit grants. Markers get no table privileges that return rows: every marking table's select policy is `(select public.is_staff_admin())`.
- An `audit_log` row (with `reason` where the action asks for one) in the same transaction as every staff change (Builder's call 13 says what counts for a marker's draft).
- The web app never holds the service-role key. Nothing marker-facing (function result, page, email, log) contains a first name, last name, email, booking id or student id. Families read nothing in this phase.
- Reasons: trimmed, 3 to 300 characters (`public.script_resolution_reason`). Time rules take `p_now timestamptz default null` read through `public.paper_clock`. Times are `timestamptz`, shown in `Europe/London` (`apps/web/src/lib/london-time.ts`).
- Exact values: hold 2 hours; marking picture links 120 seconds; save debounce 800 ms; at most 200 operations per save; a stroke at most 1,500 points; a text note at most 500 characters; at most 500 live annotations per page per marking; note to the lead at most 1,000 characters; at most 200 questions per exam, 3 levels deep; a maximum mark between 0.5 and 100; mark scheme PDF at most 20 MB; phone means a viewport under 600 px wide.
- Exact words: "Next script", "Name hidden", "Name visible", "Marking needs a computer or an iPad.", "Saved", "Saving…", "Nothing left to mark for now.", "NR" (no response).
- New migrations start at `20261122000001_*`; new pgTAP files start at `038`. To change a Phase 2 function, copy its **latest** definition (search the migrations for its last `create or replace`) and say in the header comment what was added.
- Tests run on the local copy only: `npm run db:test:local`, `npm run fn:test:local`, `npm run proc:test`, `npm test -w @stem/web`, `npm run e2e:local -w @stem/web`. Never run `db:push`, `fn:deploy`, `vercel`, `fly deploy`, `supabase config push`, anything with `--linked` or `--remote`, or the Next.js upgrade. Never deploy or push.
- `e2e:local` starts its own server on port 3005. If something already listens there, do not stop it: ask the person running the plan.
- No personal data in logs, job errors, alerts or exception details. No GPL or AGPL libraries. No new paid services.
- Work on branch `phase3-marking`, one commit per task, each message ending with the `Co-Authored-By:` line that the session's attribution rule gives.
- Copy: UK English, short plain sentences, as in the release notes. Staff pages keep the current staff look (`AppShell`, the existing Tailwind tokens); `apps/web/DESIGN.md` says not to apply the public style to staff pages. Follow `apps/web/PRODUCT.md`: calm, fast, no surprises; iPad with touch and Pencil must work. Examiner red and green are used only for marks on the page, never for interface chrome.

## Review Focus

1. A marker's hold runs out while they are still working (a long question, a break): the next save is refused in plain words, nothing they saved is lost, nobody's work is overwritten, and they carry on if the piece is still free. Tests: Task 6 `save_after_hold_expired_refused_and_work_kept`, Task 5 `expired_piece_resumes_for_same_marker`.
2. A palm rests on the iPad while the Pencil writes, or a finger drags to scroll with the pen tool chosen: no stray marks, and the page scrolls. Tests: Task 11 `touch_while_pen_down_is_ignored`, `finger_pans_with_a_draw_tool_selected`; Task 12 browser test `ipad_pen_draws_and_finger_scrolls`.
3. The same marker has the same piece open on a computer and an iPad: the stale screen's save is refused and it is told to reload; neither screen silently overwrites the other. Test: Task 6 `stale_rev_is_refused_never_overwrites`.
4. Two markers press "Next script" at the same moment with one piece left: one gets it, the other sees "Nothing left to mark for now."; never both. Test: Task 5 `two_markers_one_piece_never_both`.
5. A hidden area is changed while a script is half marked: its pieces go on hold, the old picture can no longer be fetched, the lead marker is told, and the marks stay. Tests: Task 7 `picture_change_holds_pieces_and_tells_lead`, Task 6 `old_marking_path_not_readable`.
