# Phase 4A: Results to families — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Once an exam's marking is approved, an admin prepares its results from the final marks, sets grade boundaries with a preview, checks the totals, signs off and publishes (now or at a chosen time); families are emailed and see marks per question, grade, a fair rank and cohort figures, and the annotated script; they can download a results statement and ask for a blind re-mark within 14 days. The made-up student and parent pages are gone.

**Architecture:** Results are a stored snapshot, one `results` row per candidate per exam, prepared from `public.script_final_marks` / `public.script_final_total` and never computed live for families. An exam's results have one state row (`exam_results`) that moves none → prepared → scheduled → published (→ withdrawn); every published value of a row is kept in an append-only `result_versions`, so a correction or a re-mark never overwrites published history. Families read only through `security definer` functions that check the caller is the candidate or a linked parent and that the results are published; tables are admin-only. Scripts stay `checked`: the reserved `final` state is not used. A re-mark is one more `remark` marking per piece, assigned by an admin to a marker who never saw the script, marked blind on the existing screen, and on completion its marks become the final marks and a new result version.

**Tech Stack:** Supabase (Postgres 17, pg_cron, Storage, Edge Functions on Deno), pgTAP; Next.js 16, React 19, Vitest, Playwright; `pdf-lib` 1.17.1 (already used for print packs). No new npm, Deno or Python packages. The processing server is not touched.

**Spec:** `docs/superpowers/specs/2026-11-20-web-platform-design.md`, sections 7.1, 7.2 (per-exam results, the annotated script and the downloadable per-exam report only) and 7.3 (approved 2026-11-20, with open decisions 4, 5 and 6 accepted); also binding: 3 (anti-goals), 12 to 15. Master plan: `docs/owner/2026-11-functional-specification.pdf`, sections 22 and 24 ("Access boundaries"); the design wins where it already decided. Phase 3B hand-over: `docs/superpowers/2026-11-25-phase3b-release-notes.md` ("Where Phase 4 plugs in"), `docs/superpowers/2026-11-26-phase3b-rulings.md`.

**Not in this plan (Phase 4B):** the student progress page, the parent dashboard with a child switcher, progress report PDFs, the staff operations dashboard with filters, academic reports and their exports (design 7.2 progress and dashboard, 7.4). Weighting several papers into one result (master plan section 22, "apply approved weighting") is not built: each exam is one paper with one result. **If the plan must be split:** Task 1 ships on its own (web only, nothing reads it); Tasks 8 to 10 (re-marks) stand alone after Task 7, because nothing before them reads a re-mark table.

## Global Constraints

- From the design, word for word: "Results reach families before an admin approved them." is an anti-goal; so is "A family sees another candidate's script, marks or rank, or a private examiner note." "Private notes to the lead marker are never shown." "Before publishing nothing is visible to families." "A different marker re-marks blind. The new mark stands whether higher or lower; the fee is refunded if the mark changes." "Every staff action that changes a script, a mark, a structure, a boundary or a publication writes an audit row with a reason where the action asks for one." "Private buckets only; pictures through signed links that expire within minutes, handed out after a permission check." "No personal data in server logs."
- Master plan, section 22: "Keep raw marks, moderated marks, final marks and grade boundaries distinct." "Permit rechecks and appeals without overwriting published history." Section 24: "Parents may not view another student's identifiable performance or private examiner notes."
- Phase 3B, binding: results read `public.script_final_marks(script)` and `public.script_final_total(script)` and nothing else, never `markings.total`. Results may be prepared and published only while `exam_marking.approved_at` is set and `marking_approval_get` does not say `stale`. Nobody but a marker changes that marker's own marks.
- Row-level security on every new table; every new table's select policy is `(select public.is_staff_admin())`. Families and markers read nothing from these tables directly. Writes only through `security definer` SQL functions with `set search_path = ''`; `revoke execute ... from public, anon`, then explicit grants; internal helpers are revoked from `authenticated` and `service_role` too. "Family" means the caller is the student of the booking or a parent linked to that student in `public.parent_children`, with an active account (`public.my_role()` is not null).
- Nothing family-facing (function result, page, email, PDF) carries another candidate's name, index number, booking, mark or rank, a marker's name or id, `markings.lead_note`, `markings.sent_back_note`, a review's notes or reasons, or an audit reason. A booking id that is not the caller's answers `not_found`, exactly as one that does not exist.
- An `audit_log` row with `reason` in the same transaction as every admin change. Reasons: trimmed, 3 to 300 characters (`public.script_resolution_reason`). A family's re-mark reason: 0 to 500 characters, never shown to markers.
- The web app never holds the service-role key; it is used only inside Edge Functions.
- Lock order, extended from Phase 3B: marker advisory key → `exam_marking` → `exam_results` → booking advisory lock → script rows in id order → units in id order → assignments and markings → `marking_reviews` → `final_marks` → `results` (in booking id order) → `result_versions` → `remark_requests` → `exam_markers`.
- Time rules take `p_now timestamptz default null` read through `public.paper_clock`. Times are `timestamptz`, shown in `Europe/London` (`apps/web/src/lib/london-time.ts`). Money is whole pence in `int`, shown as pounds.
- Exact values: cohort threshold 5; re-mark window 14 days from the first publication; re-mark fee 0 to 100,000 pence; 1 to 15 grades, labels 1 to 10 characters, below the lowest "U"; percentage to 1 decimal place; publish at most 30 days ahead; picture links 120 seconds, at most 40 pages per request; family lists capped at 500, the admin results list at 2,000, each with a `more` flag.
- Exact words: "Results", "Prepare results", "I have checked these totals", "Sign off and publish", "Publish at", "Withdraw results", "These results are being checked again.", "Too few candidates to compare.", "Changed on review", "No response", "Download results statement", "Ask for a re-mark", "Re-marked", "Families see notes written on the page."
- New migrations start at `20261126000001_*`; new pgTAP files start at `064`. To change an earlier function, copy its **latest** definition (search every migration for its last `create or replace`) and say in the header comment what was added.
- Tests run on the LOCAL stack only: `npm run db:test:local`, `npm run fn:test:local`, `npm test -w @stem/web`, `npm test -w @stem/shared`. `apps/web/.env.local` points at the LIVE project: never read it, never start `next dev` with it. `npm run db:reset` and `npm run db:push` act on the LIVE project: never run them. Browser specs run against a stand-in server on port 3006 built with the local stack's URL and anon key passed explicitly (as `apps/web/e2e-local.mjs` does from `supabase/functions/.env.test.local`); never stop whatever listens on port 3005. Timing guards `analyze` their own fixture tables first and keep the 8-second API limit with headroom; they are authoritative only with at least 2 GB of memory free (Phase 3B, Ruling R31).
- Never run `db:push`, `fn:deploy`, `vercel`, `fly deploy`, `supabase config push`, anything with `--linked` or `--remote`, or the Next.js upgrade. Never deploy or push. Memory on this computer is low: run one suite at a time; the full `e2e:local` is an owner gate unless 3 GB is free.
- No GPL or AGPL libraries. No new paid services. No card payments (the payment gateway is built last).
- Work on branch `phase4a-results`, one commit per task, each message ending with the `Co-Authored-By:` line for the model that wrote it.
- Copy: UK English, short plain sentences. Staff pages keep the current staff look (`AppShell`, the existing Tailwind tokens; `apps/web/DESIGN.md`, `apps/web/PRODUCT.md`). Family pages use the same look as "My bookings". Examiner red and green are used only for marks on the page.

## Review Focus

1. A parent of two children, a student, a parent of another child, or a signed-in stranger asks for a result, its script or its pictures by booking id, before publication, after withdrawal, or after unlinking: only the candidate and their linked parents ever get anything, and only while published; everyone else gets `not_found`, with nothing extra in the answer or the network panel. Tests: Task 6 `family_reads_only_own_children`, `nothing_visible_before_publication`, `withdrawn_results_say_being_checked_and_carry_no_marks`; Task 7 browser `another_familys_booking_is_not_found`.
2. Four candidates sat at home and forty at a centre: the home candidates see no rank, and an exam with fewer than five present candidates shows no cohort figures, so no family can work out another child's mark. Tests: Task 3 `cohort_under_five_shows_no_rank_or_figures`; Task 6 `small_cohort_family_sees_too_few_to_compare`.
3. Between the admin checking the totals and pressing publish (or before a scheduled time), a name is reported, a late script arrives, a boundary or a status changes, or the marking approval is withdrawn: nothing is published on figures nobody checked. Tests: Task 4 `publish_refused_when_results_changed_since_checked`, `scheduled_publish_skipped_when_approval_stale_or_withdrawn`.
4. A scheduled publication falls across the October clock change, two minute jobs overlap, or an admin publishes by hand in the same minute: results are published once and each candidate's family gets one email. Tests: Task 4 `scheduled_publish_happens_once_across_the_clock_change`, `one_results_email_per_candidate`.
5. A re-mark lowers the mark, or the re-marker's marks equal the old ones: the new mark stands, the family sees the new values with "Re-marked", the published history keeps the old version, no other candidate's rank or the cohort figures move, and the fee is due back only if the total changed. Tests: Task 9 `remark_lower_mark_stands_and_history_is_kept`, `remark_leaves_other_ranks_alone`, `remark_with_same_total_owes_no_refund`.
